# Security

Papyrus is built to run on one machine you control, on a loopback address, for readers you
know. This page is the honest list of what that does and does not protect you from.

## What Papyrus stores

No credentials for any manga site. Extensions authenticate to their own sites inside
Suwayomi, not here.

A connected AniList account is the exception, and not because AniList is a manga site. It
is a tracking service, and connecting stores one live credential per reader: an OAuth
token that acts as that person on anilist.co. It is encrypted with the install's
`APP_KEY`, and the AniList token section below says what that does and does not protect.

What does get stored is per reader: shelves, read state, progress, notes, reader settings,
and search history. Every one of those tables is scoped to a user, so a second reader on
the same install cannot see the first one's library. The AniList account table arrived
later, at migration 25, and is scoped the same way.

## The three secrets in the deployment

**Suwayomi's password.** It holds the credentials for every manga account configured in
it, so treat it as a secret even on loopback. Generate one rather than reusing a password
you already have:

```bash
php -r "echo bin2hex(random_bytes(24)), PHP_EOL;"
```

Put it in `.env`, which is git-ignored, and keep it out of any README or issue you file.

**`APP_KEY`.** Generated by `php artisan key:generate`. It encrypts sessions and the
AniList access token. Never commit it and never reuse it between installs, because
reusing it means a session cookie from one install is valid on another. A changed key
makes every encrypted value unreadable, including a connected AniList token, so the
reader has to connect again.

**`ANILIST_OAUTH_CLIENT_SECRET`.** The server half of the OAuth application a deployer
creates at anilist.co/settings/developer. `config/papyrus.php` reads it from the
environment and nothing writes it anywhere: it is sent in one request, the token POST to
anilist.co, and it reaches no table and no rendered page. Keep it in `.env`. The
`ANILIST_OAUTH_CLIENT_ID` beside it is the public half and is not a secret.

## AniList tokens are encrypted at rest

`anilist_accounts.access_token` is a `text` column with Laravel's `encrypted` cast, so the
database holds ciphertext and the model decrypts it only when a tracking request or the
connection check needs it. The key is `APP_KEY`; a database copy or a backup does not
yield a usable bearer token without it. `protected $hidden = ['access_token']` on
`App\Models\AniListAccount` still keeps the token out of serialization and rendered pages.

AniList issues no refresh token, so there is nothing to rotate or renew from. The
credential lasts until the token expires, which AniList sets at about a year, and the app
deletes the row on a rejected token rather than trying to refresh it.

AniList publishes no token revocation endpoint (checked 2026-10-28). Disconnecting
deletes the row, which ends this app's ability to act as the reader, but it does not
invalidate the token on AniList's side. The token remains valid there until it expires.

## A backup holds the library and some secrets

A backup pair is not a library-only copy. Its reader half carries the encrypted AniList
OAuth token in `anilist_accounts`, password hashes and remember tokens from `users`, and
every reader's library rows.

It does not carry live session rows or the `cache` table where the Suwayomi bearer and refresh
tokens live. Both tables stay in the copy so its schema matches the live database, but their
rows are removed and the file is vacuumed before it is kept.

Treat the backups folder as a secret, the same as the database itself. Copy a backup only to
a place you trust, and delete one you no longer need. The AniList token in the pair is
ciphertext, but the key is `APP_KEY` in the install's `.env`; a backup and that key
together are the credential. A backup restored on an install with a different `APP_KEY`
cannot decrypt the saved token; disconnect and connect AniList again.

## Suwayomi answers on loopback only

Two separate things, and for a long time this section described one of them while being titled
after the other.

**Where the app looks** is `SUWAYOMI_URL`, and setting it to loopback is necessary:

```dotenv
SUWAYOMI_URL=http://127.0.0.1:4567
```

**Where the server listens** is `server.ip` in `server.conf`, and this is the one that decides
whether anything outside your machine can reach your library. Suwayomi's own default is
`server.ip = "0.0.0.0"`, every interface, which it writes into that file itself. The launcher
now pins it to `127.0.0.1` on every start, so a packaged install does not need you to do
anything.

To see what it is actually bound to rather than what it was configured to be, ask the
machine:

```powershell
Get-NetTCPConnection -LocalPort 4567 -State Listen
```

`LocalAddress` of `:::4567` or `0.0.0.0` means every interface, and the pin is not in effect.
`127.0.0.1` or `::1` means loopback only. `papyrus health` prints the port and a `bound to:`
reading on the `suwayomi` and `web` lines, so it can tell you which of those you have.

Setting `SUWAYOMI_URL` alone never restricted anything. It is a URL the PHP app fetches, and a
server on `0.0.0.0` is perfectly happy to answer it from another machine. That was measured on
an install before the pin existed: the listener was `:::4567`, reachable from two non-loopback
addresses on the network, and a login as the configured reader from one of them returned the
full library.

Two risks remain that binding does not address, both measured rather than assumed:

Its CORS reflects any origin and allows credentials, so a page in any browser tab can make
authenticated calls to it.

And with `AuthMode.NONE` it resolves every request to `Admin(1)`, which means whoever can
reach it controls everything. `AuthMode.UI_LOGIN` is the setting that matters here; the
`php artisan suwayomi:check` command reports which one you are on.

## Extension stores are code you have not read

A store index is a list of extensions. Installing one runs Kotlin that scrapes a website on
your behalf, and Papyrus deliberately ships no bundled list, so you choose what runs. It
cannot tell you whether an extension is well behaved, because nobody can without reading
the source.

The Sources page asks for an explicit trust decision per store, and names the signing key
before anything is installed from it. Import asks the same question. A backup names the
extensions it needs, so when "Install the extensions this backup needs" is on, the import
first shows every store those packages come from, with its signing key and the packages it
would install. Nothing installs until you tick a store and confirm. The install then asks
the database which stores you trust at that moment, so a store revoked after the review
holds its packages. Ticking a store records that trust even if the import later fails.
"Import without extensions" imports the library and changes nothing on the server, and
Discard removes the review and its upload. An unanswered review expires after 24 hours and
its upload is deleted. Clear the checkbox, or choose "Import without extensions", for a
backup you did not make yourself.

Treat the store URL as the trust decision it is: paste one you have looked at.

## What the app already does for you

Worth knowing before deciding what to add in front of it:

- **Registration is closed in `single` mode**, which is the default. `/register` answers 404,
  and the sign-up link is hidden, so a one-reader install cannot be joined by accident.
- **Whole-install backup, restore, export and store add or remove require the install
  owner.** That is the first account, made by the browser's first-account window or by
  `php artisan users:create` (where `--admin` names an owner explicitly), and the role is
  not settable from a web request. Readers keep their own library, imports, trust records
  and profile.
- **Login is rate limited** to 5 attempts a minute, and there are separate limiters for
  two-factor and passkey challenges.
- **Two-factor authentication** is available per account, with password confirmation to
  enable or disable it.
- **Passkeys** are available per account, and `.well-known/passkey-endpoints` is public by
  necessity, since that is what a passkey provider fetches.
- **Every page image streams through a Laravel route**, with an allow-list of the two URL
  shapes and only `format`, `updateProgress`, `width` and `height` forwarded to Suwayomi. A
  page image is therefore never a request Suwayomi's REST layer can serve unauthenticated.
- **Page routes require a bearer token**, so a bare request to Suwayomi's REST endpoint gets
  a 401 and not a page.
- **The AniList callback sits behind `auth` and `verified`, and compares the OAuth state
  with `hash_equals()`**, so a crafted callback cannot bind somebody else's AniList
  account to a signed-in reader.

## Deployment modes

`single` is the default and closes registration. `shared` and `public` open it, which means
anyone who can reach the site can create an account.

**`shared` and `public` are otherwise identical.** The quota column in the README's mode
table and the moderation surfaces are aspirations: `enforcesQuotas()` and `quotaFor()` exist
and are unit tested, and no application code calls either, so `storage_quota_bytes` is
written by nothing. Section 14 of the engineering notes has the detail.

The public FAQ, privacy, terms and showcase JSON routes carry `throttle:120,1`, which is
120 requests a minute for one client. The showcase cover route is deliberately not
throttled: it serves public cache and its expensive step is a thumbnail on the
loopback-bound server. The Fortify endpoints have their own login, two-factor and passkey
limiters.

## The readiness endpoint and a same-host proxy

`/ready` is how the packaged launcher waits for the app key, the database and the pending
migrations. It answers only when `REMOTE_ADDR` is loopback, which is the direct connection
the launcher makes.

`REMOTE_ADDR` is the transport's answer, not the client's identity. If you put Papyrus behind
a reverse proxy on the same machine, every remote request reaches PHP from the proxy's
loopback address, so every remote client gets the readiness body. The body reports whether
the app key is set, whether the database answers and how many migrations are pending. It is
not a credential, but it is information worth withholding.

Do not forward `/ready` through a proxy. Keep it on the loopback listener the launcher polls,
or answer it from a separate loopback-only listener the proxy does not know about. A launcher
secret in a header is the other shape; it is deferred to a later release, so the route stays
loopback-gated with this caveat until one of the two lands.
